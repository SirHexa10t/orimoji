# Observations

What orimoji measured on real data. Why the numbers come out this way is in
[theory.md](theory.md); how they were taken is at the [end](#measured-how).

## The data

Two sibling projects gave orimoji its test data, each a kind of file it was made for:

- **catalogames' listing of Steam's catalogue**, `data/steam/steam-games.tsv` in the local copy of
  catalogames: 32,198,699 bytes, 188,759 lines, 20 tab-separated columns (app ids, review bands and
  counts, release dates, platform and language masks, tag lists, studios, names), with 58 comment
  lines at the top. A big, regular table, regenerated by a sweep now and then.
- **arterminal's three example drawings**, as arterminal saves them: a 13 KB ASCII-art poster
  ("long art"), a 1.1 KB braille drawing ("Kirino"), and a 6.4 KB drawing of coloured block
  elements ("Miku"), whose colours are terminal escapes. Small files, kept in a repository a line
  per row, which arterminal folded with its own *crumple*: canonical Huffman codes per row in
  base64, the approach orimoji's text and table squeezes grew from. Its crumpled form is
  orimoji's fold now; crumple's own codec is its version 1, still read.

`examples/data` holds copies: the three drawings as arterminal ships them, and the listing's header
with its first 400 rows.

## catalogames' listing

|---|--:|--:|---|--:|
| `table --index` | 40% | 72% | yes | 1.7 s / 0.4 s |
| `table` | 76% | 117% | yes | |
| `text --index` | 69% | 107% | yes | 1.3 s / 0.4 s |
| `text` | 87% | 126% | yes | |
| `deflate`, leaning on the line above | 95% | 173% | yes | |
| `none` | 133% | 134% | yes | |
| `pack` | 205% | 385% | yes | |
| `deflate --whole` | 53% | 100% | no | |
| `zstd`, level 19 | 38% | 72% | no | 6.6 s / 0.1 s |

Sizes are against the file, an indexed fold's with its index, kept as text; *in git* is against what
git stores for the file itself (zlib, 12,896,515 bytes). Indexed, the table squeeze comes within two
points of zstd over the whole file, is about as small in git, and is still a line per row. Into
`two-byte` letters it is 48% of the file's bytes and 24% of its width. `pack` is the wrong tool
here: the listing uses hundreds of characters, so a place among them costs more than a byte.

Indexed, the table squeeze chose, column by column: distances for the sorted `app_id`; numbers for
`reviews`; item lists for `tagids` and `feats` (`,`), with lists of their common items; spelling for
`name`, whose repeats are too few to pay twice over; and for every other column, studios included, a
list of its common values with the rest spelled out. `orimoji fold --index` reports:

```text
orimoji: 32198699 bytes folded into 12491038 (39%), with table into base64url, a line for each line
orimoji: the index, 28365 values, is in listing.index
```

The index is 295 KB of text, kept beside the folded file.

On the 400-row excerpt in `examples/data` it chooses a little differently (`pubs` as `;` lists),
since what pays depends on how often values repeat; `cargo run --release --example steam_listing`
prints the choice for the excerpt, or for a listing given as its argument.

Refolding the listing with its own tables (`--like`) takes half a second and gives the same file,
byte for byte.

## arterminal's drawings

Into base64url:

| Squeeze | Long art, 13 KB | Kirino, 1.1 KB | Miku, 6.4 KB | A line per line |
|---|--:|--:|--:|---|
| arterminal's own crumple | 29% | 43% | 18% | yes |
| `text --index` | 31% | 63% | 22% | yes |
| `text` | 30% | 63% | 42% | yes |
| `table --index` | 36% | 68% | 31% | yes |
| `deflate`, leaning on the line above | 38% | 74% | 22% | yes |
| `pack` | 98% | 64% | 58% | yes |
| `deflate --whole` | 25% | 53% | 16% | no |
| `zstd` | 23% | 56% | 15% | no |

The indexed text squeeze comes within two to four points of crumple on the larger drawings, its
index included. On Miku the index is what does it: its colours are terminal escapes, and as single
symbols they halve the fold. On the long art it costs a little more than it saves (31% against
30%): the twice-over rule works on estimates, and a few words fell on the wrong side of it. On
Kirino nothing is worth indexing, and the code table outweighs the body itself, where crumple writes
its table in a few characters a symbol.

In git, none of these beats the drawing as it is: a small, repetitive drawing is what zlib
compresses best, and the indexed text squeeze's files take 121–144% of what git stores for the
drawings themselves (zstd's, 95–128%). Folding a drawing buys a smaller checkout and fewer
characters, not a smaller repository; the listing, big and regular, gets both.

### Against crumple, part by part

For a while arterminal's crumpled form was the indexed text squeeze, measured, into base64url
(its version 2), and crumple's own codec (its version 1) made the drawings smaller. Where the
bytes went, crumple's against the fold's:

| Part | Long art | Kirino | Miku |
|---|--:|--:|--:|
| The code table | 108 → 277 | 161 → 362 | 47 → 251 |
| orimoji's header and `=== body ===` lines | +46 | +46 | +46 |
| The index, with its header options | | | +178 |
| The rows (crumple's: a line of characters and a line of colours each) | 3,761 → 3,761 | 289 → 290 | 942 → 810 |
| The palette, and the last newline | +1 | +1 | 119 → 159 |
| **All of it** | **3,899 → 4,115** | **480 → 729** | **1,138 → 1,474** |

The rows are not where it loses. Both spell the characters the same way: one Huffman code for the
drawing, and three or more of a character as the first, a run symbol and a count. On Miku the fold's
rows are the smaller, its escapes being single symbols where crumple writes a second line of colour
runs. The fold loses on the rest:

- **The table.** Crumple writes each code length as one base64 digit, and each character as its step
  from the one before, so a braille drawing's characters, all within 256 code points, cost two
  bytes each. The text squeeze writes a line per symbol and deflates them. Written crumple's way,
  its tables would take about 109, 162 and 98 B.
- **Miku's colours, kept twice:** as palette lines in the fold, and as escapes in the index. Crumple
  numbers them into the palette it carries anyway, and copies that as it is.

### Parts, against crumple

A fold into parts closes that gap where it was: the table and the colours. arterminal's version 3
gives orimoji a drawing's characters alone, a line a row, and keeps the colours as crumple did. The
characters, crumple's way against folded into parts:

| The characters | Long art | Kirino | Miku |
|---|--:|--:|--:|
| Crumple: table and rows | 108 + 3,761 = 3,869 | 161 + 289 = 450 | 47 + 554 = 601 |
| Parts: table, choices and rows | 70 + 9 + 3,704 = 3,783 | 80 + 9 + 290 = 379 | 36 + 9 + 522 = 567 |
| A folded file of the same | 4,084 | 698 | 738 |

The compact table takes 65%, 50% and 77% of the bytes crumple's does. The long art's and Kirino's
write their code lengths in a code of their own: Kirino's 81, from 3 bits to 8, take her table from
115 bytes, five bits each, to 80. Miku's 23 are too few to pay for describing a code, and stay five
bits each. The rows come out smaller where runs are many: the long art's counts in a Huffman
code of their own, Miku's with one low bit written as it is, and her blocks, whose code is a single
bit, written again where that is shorter than a run. Kirino's few runs keep Elias gamma, and her
rows the size crumple made them. Whole, with the colours and the palette as crumple keeps them,
arterminal's drawings crumple to 3,813, 409 and 1,104 B, where crumple's own codec made 3,899,
480 and 1,138, and the whole document folded made 4,115, 729 and 1,474.

Writing the table's characters as steps from the one before beats every other way of naming them,
in bits:

| The characters | Long art | Kirino | Miku | Genesis | Scattered scripts |
|---|--:|--:|--:|--:|--:|
| How many | 52 | 78 | 20 | 74 | 65 |
| Steps from the one before, in Elias gamma | 112 | 262 | 82 | 108 | 649 |
| The same, with the best low bits as they are | 112 | 262 | 82 | 108 | 600 (3 bits) |
| Distances from their mean | 513 | 1,009 | 477 | 723 | 1,799 |
| Distances from their median | 511 | 997 | 253 | 721 | 1,449 |
| Each its own 21 bits | 1,092 | 1,638 | 420 | 1,554 | 1,365 |

Low bits as they are pay only where scripts are scattered, the steps between them large.

### Runs

Both write a run's count in Elias gamma: a run of 3 is one bit, and a count takes two more each
time a run doubles. Counted on crumple's rows, where the counts are a quarter of the bits on two of
the drawings, other codes for the same counts would take:

| Bits for the runs' counts | Long art | Kirino | Miku |
|---|--:|--:|--:|
| Runs, and the longest | 1,113, of 77 | 27, of 13 | 167, of 40 |
| Elias gamma, as written | 5,245 (25% of the rows) | 73 (5%) | 793 (26%) |
| A fixed width, wide enough for the longest | 7,791 | 108 | 1,002 |
| Exp-Golomb, with the drawing's best k | 4,955 (k = 2) | 73 (k = 0) | 626 (k = 1) |
| A Huffman code of their own, its table included | ~5,300 | ~173 | ~596 |

Most runs are short (252 of the long art's are three long), and a width that fits the longest run
makes every one of them pay what the longest needs. Exp-Golomb writes a count's last k bits as they
are and the rest in gamma, so k = 0 is gamma itself.

Three or more of a character is always a run, though repeating a character whose code is short is
shorter: Miku's `█` has a 1-bit code, so `███` is 3 bits as it is and 5 as a run.
Choosing run by run would save about 17 B of Miku's 1,138, from 42 of her 167 runs, and nothing on
the other two.

### Pixels two characters wide

Miku is drawn in pixels two characters wide, as terminal art often is, a cell being about twice as
tall as it is wide: 32 of her 33 rows are pairs of one character throughout, the last being a
comment. So each pixel is spelled twice, and every run is counted in characters: her runs are all
of even length. Spelling a pixel once, on crumple's character rows (3,761, 289 and 554 B):

| | Long art | Kirino | Miku |
|---|--:|--:|--:|
| A line made of pairs marked as one, and spelled a pair to a symbol | ±0 | ±0 | −131 B (−24%) |
| A pair of one character as a unit, wherever it falls | +142 B | −3 B | −154 B (−28%) |

Taking any pair as a unit helps Miku a little more, but costs the long art, whose characters pair
by chance.

## Lines leaning on lines

The drawings again, each line squeezed on its own or leaning on the lines above:

| Each line squeezed | Long art | Kirino | Miku | An edit changes |
|---|--:|--:|--:|---|
| deflate, alone (`--lean 0`) | 48% | 87% | 46% | its line |
| deflate, leaning on the line above (`--lean 1`) | 38% | 69% | 21% | its line and the next |
| deflate, leaning on the 4 lines above | 36% | 63% | 20% | its line and the 4 after |
| deflate, leaning on the 16 lines above | 35% | 60% | 19% | its line and the 16 after |
| `text --index` | 31% | 63% | 22% | its line ¹ |
| arterminal's crumple | 29% | 43% | 18% | its line ¹ |
| *deflate over the whole file* | 24% | 47% | 15% | everything after it |

¹ And every line, if the edit rebuilds the shared code; not with `--like`.

The deflate rows count the body alone, without the folded file's header line. A code shared by the
whole file beats deflate leaning on its neighbours: deflate pays for its own framing on every line
and finds only what the lines above happen to repeat.

## What indexing buys

| | Without `--index` | With it |
|---|--:|--:|
| the listing, `table` | 76% | 40% |
| the listing, `text` | 87% | 69% |
| Miku, `text` | 42% | 22% |
| Miku, `table` | 41% | 31% |
| long art, `text` | 30% | 31% |
| Kirino, `text` | 63% | 63% |

Counted with its index, the index halves the fold where values or escapes repeat. Where nothing
repeats enough to pay twice over, as in the braille drawing, the fold says no index is needed and
is as it was; where little does, as in the ASCII art, it can cost a point.

## Measuring instead of estimating

Folded with `--measure-up-to`, the long art finds what the estimates missed: its index costs more
than it saves, so it is dropped, and the fold is back at 30%. On the listing, measuring confirms the
index: 12,786,159 bytes indexed, index included, against 24,487,121 without. Measuring the listing
takes 3.2 s against the plain fold's 1.6 s; given `--measure-up-to 100ms`, it gives up at its limit
and the fold takes no longer than without measuring.

## Memory

The listing (31 MiB) folded onto standard output, at the fold's peak:

| Fold of the listing | Time | Peak memory | With a buffer in tmpfs counted |
|---|--:|--:|--:|
| `none` | 0.1 s | 115 MiB | 119 MiB |
| `pack` | 1.1 s | 218 MiB | 222 MiB |
| `table --index` | 1.6 s | 177 MiB | 180 MiB |
| `table --index --measure-up-to 1h` | 3.2 s | 186 MiB | 202 MiB |
| the same, the indexed fold held in memory | 3.3 s | 205 MiB | 208 MiB |
| `auto --index` | 5.4 s | 270 MiB | 286 MiB |
| `auto --index --measure-up-to 1h` | 7.1 s | 270 MiB | 286 MiB |
| the same, the folds held in memory | 7.2 s | 331 MiB | 334 MiB |

At its peak a fold takes several times its input, most of it the squeeze's own work: the table
squeeze's model of every column, pack's numbers. `auto` peaks where `pack` does, the wrong tool for
the listing but still tried.

Measuring, the indexed fold (12.5 MB) waits in a temporary file while the fold without the index is
made, which keeps 19 MiB out of the fold's memory; through `auto`'s four folds and the measurement,
61 MiB. Here the file was in a tmpfs `/tmp`, so the bytes stayed in the machine's memory (the last
column): on a disk they leave it. The rows "held in memory" are the same build with nowhere to
write the file (a `TMPDIR` that doesn't exist), which it falls back from.

Two changes went with buffering. A fold used to hold its body twice at its end, as lines and as the
folded text: `pack` peaked at 380 MiB and `none` at 243 MiB. And `auto` used to fold the squeeze it
chose a second time: `auto --index` took 7.4 s and peaked at 413 MiB.

## Files folded together

Files folded together share one unit, its code and its index learnt over all of them and kept once,
in an `.orinv` (`cargo run --release --example folded_together -- FILE…`). Where they spell alike,
it pays; where they don't, one code for all of them spells each worse than its own would, and the
unit kept once doesn't make up for it. The three drawings take 6,158 bytes together, the `.orinv`
(378 bytes) included, against 5,449 each alone in an `.ori`: 13% more. They have few values in
common (the escapes are the coloured drawing's alone), and each draws with characters of its own.
Shared alone, the index saved little either: 6,211 bytes in all, against 6,235 with an index each,
when indexes were kept beside folded files.

Genesis, a chapter a file (`examples/data/biblical_text_multiple`: 199,246 bytes in 50 files), with
the text squeeze into base64url. The whole book is the chapters joined, 199,295 bytes, a blank line
between chapters, as `tests/chapters.rs` builds it:

| Genesis | Folded | Index | In all |
|---|--:|--:|--:|
| The whole book, one file | 117,526 | 3,435 (507 values) | 120,961 |
| The whole book, in parts | | | 119,475 |
| 50 chapters, each with its own index | 162,501 | 3,362 (50 indexes) | 165,863 |
| 50 chapters folded together, one index | 162,976 | 864 (117 values) | 163,840 |
| 50 chapters in parts, each its own index | | 3,362 | 150,860 |
| The whole book, one `.ori` | 119,318 | (inside) | 119,318 |
| 50 chapters, each an `.ori` of its own | 152,442 | (inside) | 152,442 |
| 50 chapters folded together: `.ori` files, one `.orinv` | 120,183 | 3,872 (the `.orinv`) | 124,055 |

Where the chapters' 42.9 KB more than the whole book go, with one shared index:

| Folded files | Whole book | 50 chapters, one index | More |
|---|--:|--:|--:|
| Lines | 115,433 | 142,804 | 27,371 |
| Code tables | 2,041 | 17,572 | 15,531 |
| Headers | 52 | 2,600 | 2,548 |
| Index | 3,435 | 864 | −2,571 |

The index is not where they lose: shared, it is smaller than the book's. The lines are. Each
chapter decides alone what is worth listing, and a word must pay for its place within that
chapter, so a chapter lists a few words, the 50 of them 117 in all, where the whole book lists 507,
and spells the rest a letter at a time. Then 50 code tables where the book has one, a line per
symbol each (in parts, 94 B each), and 50 headers. Folded with the whole book's code and index
instead (`--like`), the 50 chapters' lines take 115,433 bytes, exactly the book's: files folded
together can be as small as the one file they make, if they share one code and one index, decided
over all of them.

Folded together so, into `.ori` files and an `.orinv`, they take 124,055 bytes: the book's lines,
115,433; their unit once, 3,872 bytes of `.orinv`, of which the index's 507 words are 3,411; and 95
bytes of header a file, 35 of them the `.orinv`'s name (`biblical_text_multiple.orinv`). That is
the book's own `.ori`, 119,318 bytes, and the 50 headers.

### Together where it pays

Given together, files now fold together only where that takes less (`parts::fold_grouped`): each
file is weighed against the others, what it would save the whole by leaving estimated from counts,
and the folds decide between every file alone, all of them together, and each set the estimates
propose. In bytes, as `.ori` files and an `.orinv`
(`cargo run --release --example folded_together -- FILE…`):

| Files given together | All together | Each alone | As folded | Weighing | Together alone |
|---|--:|--:|--:|--:|--:|
| Genesis's 50 chapters | 124,055 | 152,442 | 124,055, all sharing | 69 ms | 30 ms |
| Three drawings | 6,158 | 5,449 | 5,449, each alone | 5 ms | |
| Eight chapters and two drawings | 24,687 | 24,511 | 22,438, the chapters sharing | 19 ms | 7 ms |
| 50 chapters, Kirino and the long drawing | 131,255 | 156,724 | 128,337, the chapters sharing | 116 ms | 41 ms |
| `man bash`, licenses and orimoji's sources, 1.2 MB | 651,116 | 629,087 | 629,087, each alone | 634 ms | 247 ms |

The estimate against folding: what the set takes, less what the rest take together and the file
alone, as folded, for each file (parts only, no headers):

| A file, among | Estimated | Folded |
|---|--:|--:|
| The long drawing, among the three | 492 | 475 |
| Kirino, among the three | 218 | 212 |
| Miku, among the three | 380 | 414 |
| The long drawing, among eight chapters and Miku | 1,506 | 1,505 |
| Miku, among eight chapters and the long drawing | 604 | 633 |
| Chapter 1, among the same | −438 | −459 |
| Kirino, among the 50 chapters | 443 | 501 |
| Chapter 24, among the 50 and Kirino | −1,426 | −1,541 |

It says which way every one of them goes, and within a tenth or so of how much: the file's own
lines, shared and alone, and its unit alone are measured; only what it does to the others' code,
and what it adds to the shared unit, are estimated, from the set's counts less its own.

Few files share little. Genesis's first chapters, given together, against each alone, the
`.orinv`'s name a single letter:

| Chapters | Without an index | With one |
|---|--:|--:|
| 2 | 5,840 alone (5,840) | 5,177 together (5,381) |
| 3 | 8,646 alone (8,646) | 7,490 together (7,990) |
| 4 | 11,315 together (11,330) | 9,809 together (10,573) |

Without an index, sharing saves a code table of 100 bytes or so a file, and costs each file a header
naming the `.orinv`; with one, it also saves listing the same words in every file.

## The text squeeze: a folded file against an `.ori`

The text squeeze now folds into an `.ori` wherever it keeps its index inside, as `auto` does where
it chooses it. Against the smallest folded file of the text squeeze, indexed, unindexed or measured,
the `.ori` was smaller on every one of 20 inputs in each of three alphabets (base64url, two-byte and
cjk). In base64url, by 0.6% on the whole book, 1.1% on `man bash`, 0.2% on two megabytes of a system
log, 4% on a `Cargo.lock`, 6% on the long drawing, 12% on Miku, 37% on Kirino, and 15% to 40% on
texts of a line or so, where the folded file's tables cost most (8% to 35% in the wider alphabets).
Its margin is least where the index is largest: a folded file deflates its index with its tables,
where an `.ori` keeps its words as they are. So no fold makes both to keep the smaller, which would
take half as long again.

## Measured how

On one core of a Ryzen 9 9950X3D. The alphabets folded and unfolded 1 MiB of random bytes, best of
5. Peak memory is the fold's maximum resident set; with a buffer in tmpfs counted, the peak of its
memory cgroup, which charges tmpfs pages to the fold that wrote them. An indexed fold is measured
with its index, kept as text. The listing is catalogames' local `steam-games.tsv`, from its sweep of
2026-09-26. The drawings are arterminal's examples as arterminal saves them. The size in git is zlib
at level 6, git's default for packs. `orimoji measure` made the result tables; the deflate rows
under [Lines leaning on lines](#lines-leaning-on-lines) and the whole-file compressors came from a
scratch benchmark of the same libraries, and crumple's sizes from arterminal itself. The parts, runs
and pixels of the drawings against crumple came from a decoder of crumple's version 1, run over
arterminal's `.crumpled` examples.
