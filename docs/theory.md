# Theory

How a fold works, and what each choice costs by definition, before anything is measured. What the
choices cost on real files is in [observations.md](observations.md); how a folded file is laid out,
bit by bit, is in [format.md](format.md).

## Squeeze, then fold

A fold is two steps. A **squeeze** makes the data smaller: it turns the data into fewer bits, using
what it knows or learns about it. An **alphabet** then writes those bits as characters. The two are
independent, so any squeeze's bits can go into any alphabet.

What a bit costs is the alphabet's business alone. An alphabet of N characters holds log₂ N bits a
character; UTF-8 spends 1 to 4 bytes on each character, and a terminal 1 or 2 cells. An alphabet
therefore sets three prices at once, bits per character, per byte and per screen cell, and none is
cheapest in all three: past ASCII, every character costs more bytes than the bits it adds.

A squeeze works a line at a time, every line of the input becoming a line of the folded file, or
over the whole file at once. A line at a time, the folded file diffs like the original; over the
whole file it is smaller, but an edit changes everything after it. See
[Lines, tables and diffs](#lines-tables-and-diffs).

## The squeezes

- **`none`**: the bytes as they are.
- **`pack`**: each character as its place among the characters the file uses. A line is one number
  in that base, so a line of digits costs 3.32 bits a character instead of 8. Its table, the list
  of characters, changes only when a character the file never had arrives.
- **`text`**: every line spelled in one Huffman code the whole file shares, so frequent characters
  get short codes. Three or more alike in a row are one symbol and a count. With an
  [index](#indexes), common words and terminal escapes are single symbols too.
- **`table`**: a row of cells a line, each column in the model that costs it least: numbers (a bit
  length, then the bits), distances from the number above (for sorted ids), lists of items, or
  spelling in a code the columns share. With an index, a list of the column's common values too.
- **`deflate`**: deflate over the whole file, or a line at a time, each line compressed with the
  lines above it as deflate's preset dictionary.
- **`zstd`**: Zstandard over the whole file.
- **`auto`**: folds with `table` (where the lines are rows), `text`, `pack` and `deflate` leaning on
  the line above, and keeps the smallest fold, its index included. It costs those four folds and
  no more: the fold it keeps is the one it made, not folded again.

| `base91` | `!` to `~` without `-`, `\` and `'` (z85 plus `` " , ; _ ` \| ~ ``, minus `-`) | 91 | ≈6.5 | 1 | 19% | 1 | 528 / 775 |
| `base94` | `!` to `~` | 94 | 6.55 | 1 | 18% | 1 | 49 / 177 ¹ |
| `braille` | U+2800–U+28FF | 256 | 8 | 3 | 67% | 1 | 406 / 192 |
| `two-byte` | letters of U+0080–U+07FF (Latin, IPA, Greek, Cyrillic, Armenian) ² | 1024 | 10 | 2 | 38% | 1 ³ | 305 / 98 |

¹ Reads its input as one big number, so the work grows with the square of the input's length.
orimoji folds a whole-file body in line-sized pieces for that reason, about 75 bytes each, and
these were timed that way. Every other alphabet takes a few bits at a time.

² The first 1,024 and 8,192 that keep to [the rules below](#what-a-character-must-be), in code
point order, generated by `tools/alphabet_tables.py` and frozen in `src/alphabet/tables.rs`: text
folded with them must unfold forever.

³ Greek, Cyrillic and some Latin-1 letters are "ambiguous width": a terminal set up for East Asian
text draws them two cells wide. No 1024-letter two-byte alphabet avoids them all.

*Bits wasted* is the share of the stored bits a character leaves unused: a base64 character holds
6 bits in a byte's 8, and a braille one 8 bits in three bytes' 24.

The alphabets past 8 bits a character have a few more characters than their count, a *short set*.
Folding bytes, a last character that would leave a whole byte of padding is written in a short one
instead, which holds 8 bits fewer, so the bytes come back exactly. `base91` is Joachim Henke's
basE91, spelled his way in the code's documentation; `cjk` and `cjk-ext-b` are the idea behind
qntm's base32768 and base65536.

The speeds are MiB of data a second on one core, from
[observations.md](observations.md#how-fast-the-alphabets-are): a guide to how the alphabets compare,
not a promise for other machines.

### Against base64, by definition

For the same bits, what each alphabet spends against base64:

| Alphabet | Characters | Bytes | Width |
|---|--:|--:|--:|
| `hex` | 150% | 150% | 150% |
| `base32`, `crockford` | 120% | 120% | 120% |
| `base58` | 102% | 102% | 102% |
| **`base64url`** | **100%** | **100%** | **100%** |
| `z85` | 94% | 94% | 94% |
| `base91` | 92% | 92% | 92% |
| `base94` | 92% | 92% | 92% |
| `braille` | 75% | 225% | 75% |
| `two-byte` | 60% | 120% | 60% |
| `one-cell` | 46% | 138% | 46% |
| `cjk` | 40% | 120% | 80% |
| `cjk-ext-b` | 38% | 128% | 75% |

No alphabet beats base64 on bytes, and only the dense ASCII ones (`z85`, `base91`, `base94`) beat it
on all three, by a few percent. Past ASCII, an alphabet trades bytes for characters, and for width
unless its characters are two cells wide. What git then makes of each is measured in
[observations.md](observations.md#the-alphabets-against-base64); [why](#alphabets-in-git) is below.

## What a character must be

Every alphabet past ASCII keeps to characters that survive being text:

- **No combining marks**, which stack onto the character before instead of taking a cell.
- **No right-to-left letters**, which make a terminal draw the line out of order.
- **No controls, spaces or invisible characters**, nothing unassigned, and no emoji, which some
  terminals draw two cells wide.
- **Nothing that Unicode normalization (NFC) changes**, like the Greek question mark, which turns
  into a semicolon.
- `one-cell` also takes nothing a terminal might draw two cells wide, East Asian "ambiguous"
  characters included.

## Plain text, and the space it wastes

Text as people write it spends a byte or more on each character, but uses few of the values those
bytes can hold:

| Text of | Characters | Count | Bits per character | UTF-8 bytes | Bits wasted | Packed into base64 |
|---|---|--:|--:|--:|--:|--:|
| bits | `0 1` | 2 | 1 | 1 | 88% | 17% |
| decimal digits | `0-9` | 10 | 3.32 | 1 | 58% | 55% |
| hex digits | `0-9 a-f` | 16 | 4 | 1 | 50% | 67% |
| lowercase letters | `a-z` | 26 | 4.70 | 1 | 41% | 78% |
| lowercase letters and digits | `a-z 0-9` | 36 | 5.17 | 1 | 35% | 86% |
| letters and digits | `a-z A-Z 0-9` | 62 | 5.95 | 1 | 26% | 99% |
| printable ASCII | space to `~` | 95 | 6.57 | 1 | 18% | 109% |
| Hebrew letters | `א` to `ת` | 27 | 4.75 | 2 | 70% | 40% |
| Russian letters | `А` to `я`, `Ё` and `ё` | 66 | 6.04 | 2 | 62% | 50% |
| braille art | U+2800–U+28FF | 256 | 8 | 3 | 67% | 44% |
| box-drawing art | U+2500–U+257F | 128 | 7 | 3 | 71% | 39% |
| block art | U+2580–U+259F | 32 | 5 | 3 | 79% | 28% |
| everyday Chinese | the 3500 of China's list of commonly used characters | 3500 | 11.77 | 3 | 51% | 65% |

*Packed into base64* codes each character in just the bits its set needs, as the `pack` squeeze
does (a line of digits becomes one number in base 10), folds that into base64, and compares it with
the text as UTF-8. It works line by line, so the text still diffs.

These are the least a text wastes. Real text wastes more, since it uses its characters unevenly
and repeats itself, and that is what the other squeezes take back. Packing alone does nothing for
text that already uses most of ASCII, and harms text that uses more than 256 characters: a place
among them costs more than a byte.

## Words from a fixed list

Packing still pays for every spelling its characters allow, and most never occur: no weekday is
spelled `xqzv`. When a field holds one word from a fixed list, list the words that do occur, and
write each as its place in that list. The number costs only the bits the list's length needs,
however long the word is:

| A word from | Words | Average length | As text, bits | Packed, bits | As an index, bits | Saved over text |
|---|--:|--:|--:|--:|--:|--:|
| `true`, `false` | 2 | 4.5 | 36 | 21.2 | 1 | 97% |
| log levels, `error` to `trace` | 5 | 4.6 | 36.8 | 21.6 | 2.32 | 94% |
| weekdays | 7 | 7.14 | 57.1 | 33.6 | 2.81 | 95% |
| HTTP methods | 9 | 4.89 | 39.1 | 23.0 | 3.17 | 92% |
| months | 12 | 6.17 | 49.3 | 29.0 | 3.58 | 93% |
| cracklib's small word list | 54,763 | 8.0 | 64.0 | 43.4 | 15.74 | 75% |

*Packed* is each character in just the bits its set needs: 4.70 for a letter, or 5.43 for the 43
characters the word list uses.

`orimoji::words` does this for lists a program gives it, and the table squeeze does it by itself
under an [index](#indexes), learning each column's list from the file:

- **The list must keep its meaning.** Words may be added at its end, but never removed or
  reordered, or old text unfolds into other words. The table squeeze hands its list back as the
  index; a fold that keeps an older fold's tables keeps its index as it was, and an index that only
  grew at its end still unfolds what was folded with it.
- **Several fields make one number.** A weekday and a month are one of 7 × 12 = 84 pairs, so one
  number below 84 holds both, in 6.39 bits rather than 3 + 4 whole ones; a `words::Record` of any
  fields works the same way.
- **A word off the list needs a way out:** the table squeeze keeps `<esc>` in every list, followed
  by the value spelled out.
- **The same trick runs backwards:** BIP-39 turns every 11 bits into one of 2048 words, so that
  people can write a key down.

## Indexes

An index is the list a fold writes values as places in: a column's common values, or the common
words and terminal escapes of a text. The list costs space too, so it has to pay for itself, and
orimoji asks it to pay twice over:

- A value goes into it only if it saves at least twice the space its line takes.
- A list that would take over half the space it saves is left out altogether, and its column is
  coded as if there were no index.

The savings are estimates (a spelled character is guessed at 5 bits, a body bit at a sixth of a
byte, as in base64), and a list is one more thing for whoever keeps the folded text to look after,
so a list that only just pays isn't worth having. Indexing is off unless a fold asks for it, since
a fold without an index is simpler to follow; on, it is usually much smaller.

Estimates can be wrong both ways, and a fold can measure instead. Given a time limit
(`--measure-up-to`), a fold whose estimates kept an index also folds without one. It keeps whichever
comes out smaller, the index counted as the text it is kept as; a tie goes to the fold without, as
the simpler. Both folds are complete when they are weighed, so the one kept is given back as it was
made, not folded a third time. Measuring takes about as long again as the fold itself, so the limit
caps it: past it, the second fold is given up where it stands, and the estimates' choice is kept.
The measurement weighs the whole index against none; it doesn't try lists one by one.

Weighing two folds means having both, but not both in memory. While the second is made, the first
waits: in memory while it is small, and past 8 MiB in a temporary file. On Unix the file loses its
name the moment it is opened, so it is gone with the fold, however that ends. `auto` weighs its
folds the same way, the smallest so far waiting while the next is made. Folding files, the
temporary file goes beside them, on their disk; otherwise into the system's temporary folder
(`TMPDIR`). Where that folder is itself in memory (a tmpfs `/tmp`), the waiting fold leaves the
fold's memory but not the machine's, and the file is better put on a disk.

The index doesn't go into the folded text. It comes back beside it, for the caller to keep where it
suits: inside a file format of its own, in a file beside the text, or once for many texts. Texts
folded together share one index, every value any of them lists, sorted; each text still decides
alone what is worth listing, and one that lists nothing doesn't need the index at all. A fold that
was asked to index says what became of it: no index (nothing paid twice over, so there is nothing
to keep and the text unfolds alone), or the index to keep.

A folded text that needs an index says so in its header, with how many values it was folded with
and a fingerprint of them, so unfolding without the index, or with another, is refused rather than
read wrong. An index that only grew at its end still fits the texts folded before it grew.

## Lines, tables and diffs

A file squeezed whole changes from the first edit on, so a diff of it says nothing. Squeezed a line
at a time, it diffs like the original, at a price: every line pays for its own start and end, and a
line can only use what it knows about the others.

| Each line squeezed | An edit changes |
|---|---|
| alone | its line |
| leaning on the line above | its line and the next |
| leaning on the k lines above | its line and the k after |
| in a code or tables the whole file shares | its line; every line, if the tables are rebuilt |
| *the whole file at once* | everything after it |

A shared code is the best of these: it knows the whole file, and costs each line only its own
symbols. Its weakness is the rebuild: an edit can shift which symbols are common, and a code learnt
afresh then changes every line. Folding a new version with the old fold's tables instead (`--like`)
keeps every unchanged line as it was; what the old tables lack is spelled out through `<esc>`, a
little larger, until the next fresh fold. A table column coded by distance leans on the row above,
so an edit there changes its row and the next.

## Alphabets in git

Git stores every object zlib-compressed, so what a folded file costs a repository is what zlib
makes of it, not its size on disk.

Zlib takes back most of what an ASCII alphabet wastes, but not what a multi-byte one does: it codes
byte by byte, so the bytes every character repeats (the lead bytes of UTF-8) still cost bits. Data
written in base64's own 6-bit units, as some formats are, keeps its repeats as repeats in base64
text, where zlib finds them; every other alphabet cuts across those units. So base64 is the
smallest alphabet in git: the dense ASCII ones at best break even with it, and the multi-byte ones
cost a fifth more or worse.

A folded file is smaller in git than the original only when the squeeze takes away more than zlib
would have. Big, regular data gets there; small files that zlib already compresses well don't, and
folding them buys a smaller checkout and fewer characters rather than a smaller repository.
